# COST CONTROL CENTER — Build Specification for Claude Code / VS Code

> Build this system end-to-end. Do not just create mock screens. Implement the database, authentication, provider connectors, synchronization jobs, cost normalization, budgets, alerts, audit logs, and setup wizard. Where a provider API does not support a real hard spending cap, do **not** fake one: clearly mark the control as `Alert only`, `Provider hard limit`, or `Emergency shutdown automation`.

## 1. Product goal

Build a private web application that gives me one place to understand and control monthly spending across:

- Google Cloud projects and billing accounts
- Gemini API usage billed through Google Cloud projects
- OpenAI API organizations/projects
- Anthropic / Claude API organizations/workspaces
- Future providers such as AWS, Vercel, Render, Supabase and Meta Ads through an adapter/plugin architecture

The main problem is that I currently have many Google Cloud projects under the same organization/billing setup, and checking usage one project at a time is slow and confusing. I want a single dashboard that automatically discovers what I have access to, shows current month spend per project/site/provider, lets me assign monthly budgets, and alerts me before spending becomes dangerous.

The product must prioritize **cost visibility, safety, least privilege, and prevention of surprise charges**.

---

## 2. Important terminology and accounting model

Do not assume a Google Cloud `Project` is always equal to a website.

Create these entities separately:

1. **Provider Account** — e.g. Google Cloud organization/billing account, OpenAI organization, Anthropic organization.
2. **Provider Resource** — e.g. GCP project, OpenAI project, Anthropic workspace.
3. **Managed App / Site** — my business-level name such as `Reshet Times`, `Mishpatly`, `Silver`, etc.
4. **Cost Allocation Rule** — maps one or more provider resources to a Managed App / Site.

A site can use resources from multiple providers, and a provider resource can optionally be allocated across multiple sites when reliable tags/labels exist.

If several websites share one single Google Cloud project with no resource labels that distinguish them, the system must explicitly display:

> `Exact per-site cost cannot be determined from billing data because these sites share the same GCP project/resources without sufficient labels.`

In that case allow manual allocation percentages, but visually label them as **estimated**, never exact.

## 4. Security requirements — mandatory

This system will handle billing/admin credentials. Treat security as a first-class feature.

### Never do this
- Never store Google account passwords.
- Never ask for credit card numbers.
- Never store plaintext API keys in the database.
- Never request `Owner` permission simply because it is convenient.
- Never expose provider tokens to the browser.
- Never log secrets, authorization headers, API keys or OAuth refresh tokens.

### Required security design
- Admin authentication with MFA-ready architecture.
- Server-side encrypted provider credentials.
- Prefer Secret Manager for long-lived provider secrets.
- CSRF protection for state-changing actions.
- Secure cookies: `HttpOnly`, `Secure`, `SameSite`.
- Rate limiting on auth and connector endpoints.
- Audit log for every sensitive action.
- Re-authentication / confirmation modal for dangerous actions.
- Least-privilege IAM instructions generated by the setup wizard.
- Environment separation: dev/staging/prod.
- No production secrets in `.env.example`.

### Audit log must include
- actor
- action
- provider
- resource
- old value
- new value
- timestamp
- result
- error summary if failed
- request correlation id

## 5. Google Cloud integration — Phase 1 priority

This is the most important connector.

### 5.1 Connection method

Support a recommended **central monitoring service account** flow.

The setup wizard should:

1. Ask for Google Cloud Organization ID if applicable.
2. Ask for Cloud Billing Account ID(s).
3. Generate exact IAM instructions for the service account.
4. Test permissions.
5. Discover projects automatically.
6. Show which billing account each project is linked to.
7. Let the user select which projects should be managed.

For read-only discovery/cost visibility, use the smallest permissions possible.

For creating/updating budgets, request additional billing budget permissions only when the user enables that feature.

Do not grant billing-payment-management permissions unless a future feature genuinely requires them.

### 5.2 Google APIs to use

Implement using official Google Cloud APIs/services:

- Cloud Resource Manager API — discover/list projects and hierarchy
- Cloud Billing API — billing account/project associations
- Cloud Billing Budget API — list/create/update/delete project/billing budgets
- Cloud Billing export to BigQuery — detailed cost and usage analytics
- Pub/Sub — programmatic budget notifications

### 5.3 BigQuery billing export

The system must support Google Cloud Billing export to BigQuery because it provides the detailed cost dataset needed for a useful dashboard.

Setup wizard should detect whether the billing export exists. If not, provide a one-time guided setup checklist.

Support:
- Standard usage cost export
- Prefer Detailed usage cost export when available

Store configuration:
- GCP billing account id
- export project id
- BigQuery dataset id
- standard cost table prefix/reference
- detailed cost table prefix/reference
- timezone for reporting

### 5.4 Google cost synchronization

At minimum synchronize:
- current calendar month
- previous calendar month
- daily totals
- project totals
- service totals
- SKU totals when useful
- credits/discounts
- taxes only if present in data and meaningful
- effective/net cost

Show both:
- `Gross cost`
- `Credits/discounts`
- `Net cost`

Do not double count credits.

### 5.6 Google project budget controls

Allow a monthly budget per Google Cloud project.

The user must be able to enter, for example:

```text
silver: 100 USD/month
mishpatly: 80 USD/month
eilatimes: 120 USD/month
```

Create/update the provider budget via the Cloud Billing Budget API where supported.

Default thresholds:
- 50%
- 75%
- 90%
- 100%

Allow custom thresholds.

### 5.7 CRITICAL: distinguish alerts from hard caps

Google Cloud budgets normally monitor spending and send alerts; they are not automatically a hard shutdown by themselves.

Implement three clearly separate modes:

#### Mode A — Monitor only
- Dashboard tracking
- No provider changes

#### Mode B — Budget alerts
- Create Google budget + thresholds
- Email alerts
- Pub/Sub listener

#### Mode C — Emergency shutdown automation
Optional and OFF by default.

If explicitly enabled for a project, the application may execute an emergency action after a configured threshold, such as disabling billing for that project.

Before enabling this mode, show a strong warning:

> Disabling Google Cloud billing can stop services in the project and may make resources unavailable. This is an emergency control, not a normal budget feature.

Require:
- checkbox confirmation
- typed confirmation using project id
- optional grace threshold, e.g. 110%
- audit log
- email immediately before/after action
- manual re-enable process

Never silently enable emergency shutdown.

### 5.8 Forecasting

Create simple explainable forecast logic:
- MTD spend / elapsed days * days in month
- optional trailing 7-day run-rate forecast

Show:
- `Projected month-end cost`
- `Projected budget overrun`
- estimated date budget will be reached

Do not present forecast as guaranteed.

Do not hard-code business logic directly into Google/OpenAI/Anthropic controllers.

Create a provider interface similar to:

```ts
interface BillingProviderAdapter {
  provider: ProviderType;

  testConnection(): Promise<ConnectionTestResult>;
  discoverAccounts(): Promise<ProviderAccount[]>;
  discoverResources(accountId: string): Promise<ProviderResource[]>;
  syncCosts(input: CostSyncInput): Promise<NormalizedCostRecord[]>;
  getBudgets(): Promise<ProviderBudget[]>;
  setBudget?(input: SetBudgetInput): Promise<BudgetActionResult>;
  getLimits?(): Promise<ProviderLimit[]>;
  setLimit?(input: SetLimitInput): Promise<LimitActionResult>;
  disconnect(): Promise<void>;
}
```

Future adapters:
- AWS
- Vercel
- Render
- Supabase
- Meta Ads

Every adapter must declare capabilities:

```ts
{
  canReadCosts: true,
  canReadBudgets: true,
  canWriteBudgets: true,
  hasProviderHardCap: false,
  supportsEmergencyShutdown: true,
  supportsProjectBreakdown: true
```

UI must be capability-driven.

## 21. Provider truth vs internal control

This is a non-negotiable product rule.

Every budget/limit UI must expose its true enforcement behavior.

Use these exact conceptual statuses:

1. **Internal alert only** — our database watches spend and sends alerts; it does not stop provider usage.
2. **Provider budget/alert** — a budget exists at the provider, but it might still not stop usage.
3. **Provider hard limit** — the provider itself rejects additional usage after the limit, where supported/configured.
4. **Emergency shutdown automation** — our automation performs a destructive/provider-level shutdown action after a threshold.

Never display the word `Hard cap` unless the underlying provider truly enforces it.

## 22. Google-specific safety note

Google Cloud Billing budgets are excellent for monitoring/alerts but a budget itself should not be presented as guaranteed spend prevention.

If implementing automated billing disablement:
- make it explicit and opt-in
- explain operational impact
- account for notification/data delay
- never promise exact cutoff at the budget dollar
- log every action
- create recovery instructions

Cost reporting can be delayed, so an emergency action may occur after actual spend has already exceeded the nominal threshold.

## 30. Development rules for Claude Code

1. Inspect the existing repository before changing anything.
2. Create a git backup/branch before major changes.
3. Do not delete existing data or functionality without explicit reason.
4. Implement incrementally and run tests after each major step.
5. Use real provider APIs — no fake success states in production paths.
6. Mock providers only in automated tests/demo mode.
7. Validate API permissions before claiming a connector is active.
8. Make all sync operations idempotent.

## 34. HARD STOP / AUTOMATIC SITE SUSPENSION WHEN BUDGET IS EXCEEDED

This is a required core feature, not only a future idea.

I explicitly accept that a website, API, AI feature, or project may temporarily stop working when its configured hard monthly budget is reached. The purpose is to prevent unexpected charges from continuing beyond the amount I approved.

### 34.1 Two budget thresholds per site/project

Every managed site/project/provider connection must support:

- `warning_limit_percent` — default 80% of the monthly budget.
- `hard_limit_percent` — default 100% of the monthly budget.
- `hard_stop_enabled` — explicit ON/OFF toggle per site/project.
- `auto_resume_next_billing_cycle` — optional setting.
- `manual_resume_requires_budget_increase` — configurable safety setting.

Example:

- Monthly budget: $100
- At $80: warning email + dashboard warning. Service continues running.
- At $100: if Hard Stop is enabled, execute the safest supported provider-specific stop action to prevent further usage/cost.

### 34.2 Provider-aware enforcement

Do NOT pretend all providers support identical hard spending caps.

For every provider, implement a capability adapter that reports one of:

- `PROVIDER_NATIVE_HARD_LIMIT`
- `AUTOMATED_SERVICE_SHUTDOWN`
- `BILLING_DISCONNECT`
- `API_KEY_DISABLE_OR_ROTATION`
- `MANUAL_ACTION_REQUIRED`
- `MONITORING_ONLY`

Use the safest technically supported method available for that provider and account type.

For Google Cloud, where appropriate and explicitly enabled, the system may use programmatic budget notifications plus an automated billing/service shutdown workflow. Before executing a destructive stop action, verify that the affected billing account/project/site mapping is correct.

Never disable an entire shared Billing Account when only one website/project exceeded its limit. Scope the stop action as narrowly as technically possible.

### 34.3 Shared Google organization / billing account safety

A Google organization such as `reshetimes-org` can contain many projects/sites.

Therefore:

- Budgets and Hard Stop rules must be assignable PER PROJECT / PER SITE.
- One site reaching its limit must NOT automatically stop unrelated sites.
- Show the Google Project ID, site mapping, billing account and affected resources before enabling Hard Stop.
- If multiple sites intentionally share the same Google project, display a warning that a project-level shutdown will affect all sites using that project.

### 34.4 Dashboard status after automatic suspension

When a Hard Stop occurs, show a prominent red status card in Hebrew RTL similar to:

**האתר הושהה עקב חריגה מתקציב**

- אתר: `{site_name}`
- ספק: `{provider}`
- תקציב חודשי: `{monthly_budget}`
- שימוש החודש: `{current_spend}`
- תאריך ושעת עצירה: `{stopped_at}`
- סיבת העצירה: `הגעה לרף התקציב שהוגדר`
- פעולה שבוצעה: `{provider_stop_action}`

Message:

`השירות הושהה אוטומטית כדי למנוע חיובים נוספים. ניתן להגדיל את התקציב ולאחר מכן להפעיל מחדש את השירות.`

Provide actions:

- `הגדל תקציב`
- `הפעל מחדש`
- `פתח פירוט חיובים`
- `צפה ביומן האירועים`

### 34.5 Email notifications

Send email notifications at minimum for:

- 50% budget usage (optional configurable)
- 80% warning threshold
- 90% critical warning (optional configurable)
- 100% / hard threshold reached
- Hard Stop successfully executed
- Hard Stop execution failed
- Service manually resumed
- Service automatically resumed at the beginning of a new billing cycle

The Hard Stop email must clearly say that the website/service may currently be unavailable because the configured spending ceiling was reached.

### 34.6 Event / audit log

Every budget-related action must be permanently logged:

- site/project
- provider
- billing account where applicable
- configured monthly budget
- actual spend at event time
- percentage consumed
- event type
- stop action requested
- stop action result
- provider response/error
- timestamp
- actor: SYSTEM or USER
- user who changed the budget
- previous budget
- new budget
- resume action and timestamp

Important event types:

- `BUDGET_WARNING`
- `BUDGET_CRITICAL`
- `HARD_LIMIT_REACHED`
- `HARD_STOP_STARTED`
- `HARD_STOP_SUCCEEDED`
- `HARD_STOP_FAILED`
- `BUDGET_INCREASED`
- `MANUAL_RESUME`
- `AUTO_RESUME_NEW_CYCLE`

### 34.7 Increase budget and resume workflow

Implement a simple recovery workflow:

1. User opens the suspended site.
2. Dashboard explains exactly why it was stopped.
3. User clicks `הגדל תקציב`.
4. User enters the new monthly budget.
5. System saves/synchronizes the new limit where supported.
6. System checks whether the site is now below the new hard threshold.
7. User can click `הפעל מחדש`.
8. System reverses only the stop action previously performed by this application.
9. Verify service health after resume.
10. Log the entire action.

Never blindly re-enable resources that were disabled manually outside this application.

### 34.8 New billing-cycle behavior

At the start of each provider's new monthly billing cycle:

- reset application-side monthly threshold state;
- keep historical usage and audit logs;
- calculate against the new billing period;
- if `auto_resume_next_billing_cycle = true`, safely restore only resources that this system automatically suspended;
- send an email confirming the new billing cycle and automatic restoration.

### 34.9 Cost synchronization frequency and overshoot warning

Hard Stop cannot guarantee that final provider charges will equal the budget to the exact cent because cloud/provider usage and billing data can arrive with delay.

Therefore:

- poll/synchronize cost data frequently within provider API quotas;
- consume real-time/programmatic budget notifications when available;
- show the last successful cost-sync timestamp;
- show a warning that delayed provider billing data can cause a small overshoot beyond the configured threshold;
- never label an application-side shutdown as a guaranteed bank/card-level payment cap.

### 34.10 Required UI indicator

Every site/project row must show a clear protection status:

- `🟢 מוגן — עצירה אוטומטית פעילה`
- `🟡 התראות בלבד`
- `🔴 עבר תקציב — השירות הושהה`
- `⚠️ לא ניתן לבצע עצירה אוטומטית אצל ספק זה`

The user must be able to understand the protection level without opening the provider console.

### 34.11 Safety rule

No Hard Stop may be enabled until the application has positively verified the provider resource/account/project that will be affected.

Before first activation, show a one-time confirmation containing the exact site, provider, project/account identifier, monthly budget, and what technical action will occur at the hard threshold.

After confirmation, normal automatic enforcement must require no manual confirmation each month.
